# Tutorial: colocando o CrowdAcadêmico para rodar na sua máquina

Do zero até o painel aberto no navegador, falando com o banco: banco de dados (Supabase ou Postgres local), backend (Nest) e frontend (React). Tudo gratuito.

Siga na ordem. Não pule etapas mesmo que pareçam óbvias.

---

## ✅ Checklist rápido (para quando você já fez isto pelo menos uma vez)

Se travar em algum item, a parte indicada tem a explicação completa.

- [ ] Instalar Node.js LTS, Git e VS Code (Parte 0)
- [ ] Banco pronto: Supabase (Parte 1) ou Postgres local (Parte 2), com os 8 arquivos `.sql` rodados na ordem `01 → 08` e o `ALTER ROLE app_nestjs LOGIN PASSWORD '...'` (**obrigatório**)
- [ ] `git clone` do repositório
- [ ] Backend: `cd nest` → `npm ci` → criar o `nest/.env` a partir do `nest/.env.example` → `npm run start:dev` (Parte 4)
- [ ] Frontend: `cd react` → `npm ci` → criar o `react/.env` a partir do `react/.env.example` → `npm run dev` (Parte 5)
- [ ] Na raiz do repositório: `npm ci` (só se for fazer commit: liga a checagem de lint)
- [ ] Testar: `http://localhost:3000/health` (backend) e o link que o Vite mostrar, geralmente `http://localhost:5173` (o painel)
- [ ] Antes de sair: `git add` / `git commit` / `git push`. O computador da escola não guarda nada

> **`npm ci` ou `npm install`?** Para instalar um projeto clonado, use `npm ci`: instala exatamente as versões do `package-lock.json` e não altera o arquivo. O `npm install` pode reescrever o lockfile (com npm de outra versão, como na escola, aparecem mudanças falsas no Git). `npm install` só quando for adicionar ou trocar um pacote.
>
> **Se o PowerShell bloquear o npm** ("a execução de scripts foi desabilitada neste sistema"), digite `cmd` e Enter, e rode os comandos ali.

## 🏫 Computador que reseta todo dia (escola)

1. **Guarde os instaladores, não só os links.** Baixe uma vez os instaladores do Node.js, Git e VS Code (e do PostgreSQL, se usar o banco local) e salve no Google Drive ou num pendrive. Na escola, é só copiar e instalar.
2. **Leve os arquivos que não vão para o Git:** `nest/.env` e `react/.env` (com as chaves). Opcional: o `.fake-gateway.json` da pasta `nest`, a memória do provedor de pagamento de teste (ver `.Tutorial-plataforma-pagamento-sandbox.md`).
3. **O código vem sempre do GitHub** (`git clone`). Nunca crie um projeto Nest ou Vite novo: isso trocaria o sistema por um projeto vazio.

## Parte 1 - o banco no Supabase (o caminho de sempre)

O Supabase é um PostgreSQL de verdade hospedado na internet, com plano gratuito. Todo o `.sql` do projeto roda nele sem adaptação.

1. Crie uma conta em supabase.com e um projeto novo. Ele pede uma senha para o banco: é a senha do usuário `postgres` (o superusuário). Guarde num lugar seguro, fora do repositório.
2. No painel do projeto, abra o **SQL Editor**. Cole o conteúdo de cada arquivo de `arquivos_banco_dados/` e rode, **um de cada vez, nesta ordem**, conferindo que não deu erro antes de ir para o próximo:
   ```
   01_extensoes_enums_tabelas.sql
   02_indices.sql
   03_funcoes_seguranca.sql
   04_rls_policies.sql
   05_regras_negocio.sql
   06_grants.sql
   07_seed_dados.sql            (senha de todas as contas de demonstração: DevTcc123!)
   08_trigger_signup_usuario.sql
   ```
3. Dê login e senha ao usuário que o sistema usa (passo **obrigatório**):
   ```sql
   ALTER ROLE app_nestjs LOGIN PASSWORD 'escolha-uma-senha';
   ```
   O `01` cria o `app_nestjs` sem poder entrar, de propósito. Sem este passo, o Nest não conecta e o erro diz `role "app_nestjs" is not permitted to log in`.
4. A conexão para o `nest/.env` fica em **Connect** (ou Project Settings > Database). Use o usuário `app_nestjs` e a senha do passo 3, nunca o `postgres`. O `nest/.env.example` mostra o formato.

### Recriar o banco do zero no Supabase

Para apagar tudo e montar de novo (por exemplo, depois de mudanças nos `.sql`), rode no SQL Editor:

```sql
DROP SCHEMA public CASCADE;

CREATE SCHEMA public;
GRANT ALL ON SCHEMA public TO postgres;
GRANT ALL ON SCHEMA public TO public;
```

Depois, repita os passos 2 e 3 acima. **Pare o Nest antes**: com ele ligado, o `DROP SCHEMA` pode travar esperando as conexões dele.

### Cuidados do Supabase

- **Sem internet, o backend não conecta.** Para rede bloqueada ou apresentação sem internet garantida, o Postgres local (Parte 2) é o caminho seguro.
- **Projeto gratuito "dorme" depois de cerca de 1 semana sem uso.** A conexão seguinte falha até você clicar em **Resume** no painel do Supabase. Abra o painel de vez em quando, principalmente perto de datas importantes.

## Parte 2 - alternativa: o banco local (PostgreSQL + DBeaver)

1. Instale o PostgreSQL (versão estável mais recente). Ele pede a senha do `postgres`: use `postgres123`, sempre a mesma, em qualquer computador. Deixe a porta `5432`. O "Stack Builder" do fim pode ser fechado.
2. No DBeaver: **Nova Conexão** > PostgreSQL > host `localhost`, porta `5432`, usuário `postgres`, senha `postgres123` > **Test Connection**.
3. Botão direito em "Databases" > **Create New Database** > `crowdacademico`. Conecte nesse banco (não no `postgres`).
4. Rode os 8 arquivos na mesma ordem da Parte 1, passo 2. Em cada um: Ctrl+A e **Execute SQL Script** (Alt+X), não "Execute SQL Statement" (que roda um comando só).
5. Rode o `ALTER ROLE` da Parte 1, passo 3, com a senha `app_nestjs123`.
6. No `nest/.env`: `DATABASE_URL=postgresql://app_nestjs:app_nestjs123@localhost:5432/crowdacademico`

Se algum arquivo der erro por já existir algo (rodou duas vezes sem querer), apague o banco `crowdacademico`, crie de novo e recomece a sequência.

## Parte 3 - opcional: aplicar os `.sql` por comando (`npm run db:migrate`)

Em vez de colar os 8 arquivos no SQL Editor, um script aplica todos na ordem e guarda quais já rodaram (tabela `schema_migrations`). Detalhe técnico em `DOCUMENTACAO_BACKEND.md`, seção 12.

1. No `nest/.env`, além da `DATABASE_URL`, uma segunda linha com o **superusuário** `postgres`:
   ```
   DATABASE_URL_MIGRATIONS=postgresql://postgres:SENHA-DO-POSTGRES@db.xxxxxxxxxxxx.supabase.co:5432/postgres?sslmode=require
   ```
   - Use a **Direct connection** (porta `5432`, host `db....supabase.co`), não o pooler (porta `6543`): o script manda cada arquivo inteiro de uma vez, e o pooler não lida bem com isso.
   - Senha com caractere especial (`@`, `/`, `#`) precisa ser trocada por código `%XX` na URL. Mais simples: uma senha só com letras e números.
   - Esqueceu a senha do `postgres`? Project Settings > Database > **Reset database password**. A senha nova aparece só até recarregar a página. Trocar a do `postgres` não afeta a do `app_nestjs`.
2. Banco novo, vazio: dentro de `nest/`, `npm run db:migrate`.
3. Banco que já foi montado colando os arquivos à mão: uma única vez, `npm run db:migrate:adotar`. Ele não roda nada, só registra que os 8 já estão aplicados.

**Banco de produção** (sem contas e campanhas de demonstração): o `07_seed_dados.sql` roda só até o marcador `[07-DEMONSTRACAO]`. A primeira pessoa se cadastra pelo site e é promovida a admin uma vez, direto no banco: `INSERT INTO usuario_papel (id_usuario, id_papel) SELECT <id da conta>, id_papel FROM papel WHERE codigo = 'admin';`.

**Problemas comuns:**
- `password authentication failed for user "postgres"` (código `28P01`): a senha da `DATABASE_URL_MIGRATIONS` não é a do Supabase. Resete (passo 1) e atualize a linha.
- `◇ injected env (N) from .env // tip: ...` aparece toda vez: não é erro, é propaganda do pacote `dotenv`. O número é quantas variáveis ele leu do `.env`: se você acabou de pôr uma linha nova e o número não subiu, o arquivo não foi salvo.

## Parte 4 - o backend (Nest)

1. No terminal, na pasta do projeto clonado: `cd nest` e `npm ci`.
2. Copie `nest/.env.example` para `nest/.env` e preencha. Cada variável tem a explicação no próprio arquivo. O mínimo para subir:
   - `DATABASE_URL`: a conexão como `app_nestjs` (Parte 1 ou 2);
   - `JWT_SECRET`: o segredo do login (qualquer texto longo em desenvolvimento);
   - `CPF_ENCRYPTION_KEY` e `CPF_INDEX_KEY`: as chaves do CPF, **diferentes entre si**.
   Pagamento, e-mail e armazenamento de arquivos têm tutorial próprio (`.Tutorial-plataforma-pagamento-sandbox.md`, `.Tutorial-email.md`); sem configurar, o sistema usa os provedores de teste.
3. Suba: `npm run start:dev`. Ele reinicia sozinho a cada arquivo salvo, mas **não** relê o `.env`: depois de mudar o `.env`, Ctrl+C e suba de novo.
   - Para testar pagamentos sem o Asaas: `npm run start:dev:teste` (ver o tutorial de pagamento).
4. Teste no navegador: `http://localhost:3000/health`. Deve aparecer `{"status":"ok","banco":"conectado"}`.

Se não subir, leia a mensagem: o Nest se recusa a iniciar e diz o que falta quando a configuração está incompleta, ou quando a conexão não é como `app_nestjs`.

## Parte 6 - cuidados ao mexer no banco à mão (SQL Editor)

- **`SELECT *` em `usuario` ou `perfil_pesquisador` dá erro de permissão.** O `06_grants.sql` libera só algumas colunas dessas tabelas (o CPF cifrado fica de fora). Liste as colunas na consulta.
- **`UPDATE` manual pode não mudar nada, sem erro.** As tabelas têm regras de acesso por linha (RLS): sem dizer quem está fazendo a mudança, o `UPDATE` afeta 0 linhas em silêncio. Antes do `UPDATE`, na mesma sessão:
  ```sql
  SET app.id_usuario_atual = '<id de um usuário com a permissão necessária, ex.: o admin>';
  ```

## Parte 7 - `npm audit` mostrando vulnerabilidades

A lista de falhas conhecidas cresce todo dia, então o aviso volta de tempos em tempos mesmo sem mexer no código.

1. No computador de casa, dentro de `nest` e depois de `react` (não na raiz): `npm audit fix`
2. Conferir: `npm run build` (e `npm run lint` no `nest`).
3. Commitar os `package-lock.json`. Na escola, o `npm ci` já instala as versões corrigidas.

**Nunca use `npm audit fix --force`:** ele "corrige" rebaixando ferramentas e quebra o projeto. O que sobra sem conserto (hoje: `braces` e `sprintf-js`, só em ferramentas de teste e de geração de tipos) não vai para o sistema publicado.

## Parte 8 - meu commit foi barrado (`husky - pre-commit script failed`)

Não é defeito. A cada commit, o **husky** (o porteiro) chama o **lint-staged**, que passa o **ESLint** (o corretor do código) **só nos arquivos que vão entrar no commit**. Se achar erro, o commit é recusado. Nada se perde: os arquivos continuam como estavam.

**1. Ache os erros.** Role a mensagem para cima a partir de `✖ N problems`. Eles vêm agrupados por arquivo:

```
C:\Users\...\nest\src\1-usuario\service\usuario.service.update.ts
  12:7   error  'resultado' is assigned a value but never used   @typescript-eslint/no-unused-vars
```

- **Primeira linha:** o arquivo com problema.
- **`12:7`:** linha 12, coluna 7. No VS Code, `Ctrl+G` vai direto à linha.
- **Texto do meio:** o problema, em inglês (o tradutor ajuda).
- **Final (`no-unused-vars`):** o nome da regra. Pesquisar o nome explica a regra.

**2. Identifique o caso.**

- **A. Dezenas ou centenas de erros, em arquivos que você nem mexeu** (*"Unable to resolve path"*, *"Cannot find module"*, muitos *"Unsafe ... any"*): o "carrinho" (`git add`, ou *staged*) está incompleto, e o revisor olha uma versão pela metade. É comum depois de renomear arquivos: o nome novo entrou, a correção dentro deles não. **Solução:** ponha tudo no carrinho e repita o commit. No VS Code, na aba de controle de código, passe o mouse sobre **"Changes"** e clique no **`+`** (tudo vai para **"Staged Changes"**). No terminal: `git add -A`.
- **B. Poucos erros, nos arquivos que você mudou:** é problema real no código (variável nunca usada, tipo errado). Corrija na linha indicada.
- **C. Sem `C:\...` nem `error`, falando em `npx`, `not found` ou `ENOENT`:** a ferramenta não está instalada. Rode `npm ci` na pasta raiz e tente de novo.

**3. Conferir sem commitar (opcional).** Na pasta raiz, `npx lint-staged`. Se terminar com `✔ Done running tasks`, o commit passa. Para revisar um lado inteiro: `npx eslint src` na pasta `nest`; `npm run lint` na pasta `react`.

**4. Não conseguiu?** Mande para quem for ajudar a mensagem inteira, da primeira linha `C:\...` até `✖ N problems`: com arquivo, linha e regra, dá para resolver sem acesso ao seu computador. **Não apague nem desfaça nada para "fazer passar".**

**Só em emergência:** `git commit --no-verify -m "mensagem"` grava sem passar pelo porteiro. Avise a outra pessoa: o que o revisor barraria entra do mesmo jeito, e quem baixar pode receber código que não funciona.

Parte técnica (onde fica cada configuração e como desligar): `DOCUMENTACAO_LINT.md`, seção "Checagem no commit".
